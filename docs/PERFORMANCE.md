# 性能预算与优化（联机版）

性能是硬指标，不是收尾项。本文定义预算、手段、度量和门槛；任何阶段都不能用"先跑通再优化"绕过。

## 1. 预算（硬指标）

| 层 | 指标 | 目标 | 当前（2026-10-19） |
| --- | --- | --- | --- |
| 服务端 tick（4 人 + 4 AI） | p99 | ≤ 2.0 ms | 待 P1 实测 |
| 稳态每 tick 堆分配 | 次数 | **0**（热路径） | 协议层已 0 增长 |
| 快照编码（338 B） | 单帧 | ≤ 50 µs | **0.40 µs** |
| 快照解码 | 单帧 | ≤ 100 µs | **0.68 µs** |
| 快照大小 | p95 | ≤ 600 B | **338 B**（协议 v2，含炸弹/掉落/事件） |
| 单客户端下行 | 平均 | ≤ 20 KB/s | **8.8 KB/s**（30 Hz） |
| 房间常驻内存 | 稳态 | ≤ 256 KB | 待 P2 |
| 单核房间数 | 60 Hz | ≥ 500 | 待 P5 压测 |
| 客户端帧时间 | p95 | ≤ 16.7 ms | 现有 `test:perf` 基线 |
| 客户端每帧分配 | 热路径 | 0 | 有已知热点（见 §4） |
| 预测校正 | 每人 | ≤ 0.5 次/秒 | 待 P4 |

## 2. 已经做的

- **二进制协议**：postcard + varint，不是 JSON；单帧上限 4 KB。
- **量化**：位置 1/16 px（`i32`）、速度 1/8 px/s（`i16`），字段按 1 字节裁剪。
- **复用缓冲**：`encode_into(&mut Vec<u8>)`，热缓冲不重新分配（有单测断言容量不变）。
- **实测**：4 人 + 20 弹丸 + 事件 = **293 B**；编码 428 ns、解码 610 ns（criterion，release）。
- **统一数学**：`libm` 同时解决 native/wasm 差异与跨平台实现差异。

## 3. 按层的优化清单

### 3.1 协议与序列化（P0 已完成）

- 广播时**只编码一次**，4 个连接各自 `Bytes` 引用计数 clone，零拷贝；不要为每个客户端重新编码。
- 快照只带渲染与预测需要的字段；弹药、冷却等用 `u8`（按 1/255 归一）。
- 事件只带 `tick + kind + 两个参数`，不带字符串。
- 版本与内容哈希只在 `Hello` 出现一次，不进快照。

### 3.2 房间循环（P1/P2）

- 输入表用 `[Option<InputFrame>; 4]`，不用 `HashMap`。
- 角色/弹丸用固定容量数组 + 复用长度（`clear()`，不 `shrink_to_fit`）。
- 事件队列复用；tick 内禁止 `format!`、`String`、`println!`。
- 每房一个编码缓冲，`encode_into` 后 `Bytes::copy_from_slice` 一次，广播 clone。
- 计时用 `Instant` 绝对 deadline，不用 `sleep(16ms)` 累加；落后最多补 5 tick。

### 3.3 网络（P2）

- `TCP_NODELAY`；**关闭** `permessage-deflate`（1 KB 级帧压缩只增加延迟）。
- 快照远小于 MTU（实测 293 B），避免 TCP 分片与队头放大。
- 输入 60 Hz 一条，服务端 1 tick 抖动缓冲。
- 慢客户端：`try_send` + 丢最旧帧 + 计数，绝不阻塞房间。

### 3.4 客户端（P2/P4）

- 渲染热路径零分配：复用数组与对象池，不在 `draw` 里 `map/filter/slice`。
- **已知热点**：`MatchRunner.advance` 每 tick `new Map<string, ActorInput>()`。P1 改成预分配输入表（与 external-ai 分支的改动协调后再动）。
- WASM ABI：输入/状态走扁平 `Float32Array`，一次调用推进一步，不逐字段跨边界。
- 预测只跑本地角色与必要的世界状态；远端只插值。

### 3.5 持久化与部署（P5）

- 对局结束批量写，WAL，tick 内不做磁盘 IO。
- release 构建开 `lto = "thin"`、`codegen-units = 1`、`panic = "abort"`（构建时间换运行时）。
- tokio worker 数 = 物理核数；容器限制 CPU 时同步调整。

## 4. 度量与门槛

| 手段 | 位置 | 频率 |
| --- | --- | --- |
| 协议/核心 bench | `cargo bench -p gunbrawl-proto`（criterion） | 每次改动 |
| 客户端 FPS / heap | `pnpm test:perf`（20 局） | 每次前端改动 |
| 负载压测 | 400 bot × 100 房 × 10 分钟 | P5 及发布前 |
| 运行指标 | tick lag p99、快照字节、输入缓冲、丢帧 | 线上持续 |

CI 门槛（P5 开启）：

- `cargo bench` 结果与 main 基线比，关键项回归 **> 10%** 失败；
- `tick_lag_seconds` p99 > 20 ms 持续 5 分钟告警；
- 快照 p95 > 600 B 或带宽 > 20 KB/s 时，delta 快照从"可选"升级为"必做"。

## 5. 全量快照 vs delta：当前结论

v2 草案写的是"v1 全量，P4 再考虑 delta"。实测全量只有 **293 B**（预算 600 B），30 Hz 下 8.8 KB/s（预算 20 KB/s），**delta 现在不划算**：它增加编码复杂度、差分解码错误面和调试难度，换来的带宽余量用不上。

因此：

- v1 保持全量，但**预算写死**：p95 ≤ 600 B、带宽 ≤ 20 KB/s；
- 超过任一阈值（例如第 5 种武器弹幕同屏），delta 立即升级为必做项，按"关键帧 + 变化掩码"实现；
- 无论全量还是 delta，编码都走 `encode_into` + 广播零拷贝。
